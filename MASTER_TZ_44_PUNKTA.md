---

1. Исходный проект — существующий рабочий Telegram-бот karaoke_pro (github tendo-a11y/karaoke_pro), это основа всей разработки; сохранять рабочую функциональность; не создавать новый независимый бот.
2. Цель доработки — добавить автоматизированную передачу заказов: Гость → Telegram Bot → Backend API → KJ Panel → VirtualDJ; KJ подтверждает одной кнопкой, без ручного переноса в VirtualDJ.
3. Что сохраняется — Telegram Bot и все существующие роли (Admin, KJ, VIP, клиенты, клиент без стола), клубы, поиск, система заказов, очередь, статистика, отчётность, настройки, логика взаимодействия. Менять код только там, где нужно для нового функционала.
4. Новая архитектура — поверх существующего бота добавляются: Flask (API нового процесса), React (KJ-панель), PostgreSQL (централизованные заказы), VirtualDJ получает подтверждённые заказы автоматически.
5. Основной сценарий
   * Шаг 1: гость создаёт заказ через существующий бот (свободным текстом).
   * Шаг 2: поиск песни — старый механизм работает + дополнительно AI-поиск (Claude → Genius → варианты).
   * Шаг 3: бот показывает 3-5 вариантов; если найдено меньше — показывать фактически найденное, не выдумывать.
6. Выбор песни — гость нажимает вариант, формируются данные заказа: telegram_user_id, club_id, table_no, song_title, artist.
7. Передача заказа в backend — бот шлёт POST /api/client/order с этими полями.
8. Источник данных — старая БД и логика на первом этапе не удаляются; сначала реализовать и протестировать Telegram→Backend→PostgreSQL; миграция старых данных — отдельный последующий этап; удаление старой базы/логики без миграции запрещено.
9. Создание заказа — backend создаёт запись: id, telegram_user_id, club_id, table_no, song_title, artist, status, created_at.
10. Статусы заказа — pending (ждёт KJ), processing (в обработке, защита от двойного подтверждения), queued (передан в VDJ), playing (играет), completed (завершён), rejected (KJ отклонил), error (ошибка обработки).
11. React KJ Panel — отдельная панель на localhost:3000 для KJ.
12. Список заказов — KJ видит заказы своего клуба; минимум полей: стол, название, исполнитель, пользователь, статус, время заказа.
13. Подтверждение заказа — KJ жмёт "Подтвердить" → React шлёт PUT /api/kj/order/{id}/confirm.
14. Обработка подтверждения — backend должен: проверить существование заказа, права KJ, принадлежность клубу, текущий статус; перевести в processing; передать в VirtualDJ; получить результат; при успехе → queued; сохранить vdj_item_id, если есть; уведомить гостя; передать обновление в React.
15. Защита от двойной обработки — переход pending→processing атомарный; повторное подтверждение запрещено; заказы в processing/queued/playing/completed повторно в VDJ не отправляются; повторный запрос → 409 Conflict.
16. VirtualDJ — backend передаёт песню в VDJ (add to queue); конкретный механизм подключения определяется по факту установленной версии VDJ, несуществующий API не выдумывается; заранее нужно выяснить способы: добавления песни, получения очереди, получения текущей песни, удаления песни, получения событий изменения очереди.
17. Результат добавления в VDJ — при успехе: status=queued, гость получает уведомление.
18. Ошибка VDJ — если VDJ недоступен/не принял: status=error, KJ видит предупреждение, заказ не считается добавленным.
19. Отклонение заказа — KJ жмёт "Отклонить" → PUT /api/kj/order/{id}/reject → status=rejected, гость уведомлён.
20. Удаление из VirtualDJ — отклонение до передачи в VDJ и удаление уже добавленной в очередь песни — разные операции; если VDJ даёт vdj_item_id — сохранять его; отдельный DELETE /api/vdj/queue/{vdj_item_id}.
21. Живая очередь — React показывает актуальную очередь VDJ: №, песня, исполнитель, стол, статус.
22. WebSocket — для авто-обновления React: backend на python-socketio, frontend на socket.io-client; события: order_created, order_updated, order_confirmed, order_rejected, queue_updated, song_started, song_finished.
23. API backend (минимальный набор) — POST /api/client/order, GET /api/kj/orders/{club_id}, GET /api/kj/order/{id}, PUT /api/kj/order/{id}/confirm, PUT /api/kj/order/{id}/reject, GET /api/kj/queue/{club_id}, POST /api/vdj/queue/add, DELETE /api/vdj/queue/{vdj_item_id}.
24. Авторизация — backend не доверяет user_id/club_id от React; сам определяет: кто пользователь, его роль, клуб, активность доступа, право менять заказ; KJ одного клуба не видит заказы другого.
25. Клубы — мультиклубная логика сохраняется; каждый заказ привязан к club_id; KJ видит только свой клуб.
26. Telegram user — чётко разделять telegram_user_id и внутренний user.id, не смешивать; если используется внутренний ID — backend сам сопоставляет его с Telegram ID.
27. Номер стола — table_no сохраняется для каждого заказа, источник — существующая логика; для гостя без стола — table_no = null (или эквивалент).
28. Claude AI — анализирует свободное описание песни гостя, определяет возможные название/исполнителя/ключевые слова/варианты написания; Claude сам не считается музыкальной базой.
29. Genius API — ищет по данным от Claude: Описание → Claude → поисковые данные → Genius → результаты; в заказ идут именно выбранные гостем данные.
30. Существующий поиск — новый AI-поиск не должен сразу уничтожать старый; сохранить старую логику до полного тестирования нового; после тестирования решить: оставить оба, или заменить часть старого.
31. База данных — PostgreSQL для централизованных заказов; минимальные сущности: clubs, users, kj_operators, orders.
32. Orders (структура) — id, telegram_user_id/user_id, club_id, table_no, song_title, artist, status, vdj_item_id, created_at/confirmed_at/queued_at/playing_at/completed_at/rejected_at; точная структура согласуется с существующими моделями проекта.
33. Конфигурация — секреты не в коде, а в переменных окружения: TELEGRAM_BOT_TOKEN, ANTHROPIC_API_KEY, GENIUS_API_KEY, DATABASE_URL, FLASK_API_URL, VDJ_API_URL, VDJ_API_TOKEN.
34. Обработка ошибок — понятные HTTP-коды: 200/201/400/401/403/404/409/500/502/503; формат ошибки — JSON с success:false, error-кодом и message.
35. Сохранение существующей бизнес-логики — доработка не должна ломать сценарии ADMIN/KJ/VIP/CLIENT/NO TABLE CLIENT; все существующие функции проверяются после изменений.
36. Фаза 1 — анализ существующего karaoke_pro — до изменения кода выяснить: где создаётся/сохраняется заказ, какие модели и БД используются, как работают KJ, очередь, определение клуба/стола, VIP-заказы, клиент без стола.
37. Фаза 2 — Telegram Bot → Backend — реализовать цепочку Bot→POST /api/client/order→PostgreSQL; проверить создание заказа, корректность telegram_user_id/club_id/table_no/названия/исполнителя/статуса.
38. Фаза 3 — React KJ Panel — реализовать получение и отображение заказов, фильтрацию по статусам, подтверждение, отклонение, отображение ошибок.
39. Фаза 4 — KJ → VirtualDJ — реализовать цепочку KJ→Confirm→Backend→VirtualDJ→Queue.
40. Фаза 5 — Live Queue — реализовать VirtualDJ→Backend→WebSocket→React.
41. Фаза 6 — AI Search — добавить цепочку Описание→Claude→Genius→3-5 результатов→выбор гостя.
42. Тестирование (8 тестов)
    * Тест 1 — обычный заказ: гость→Telegram→поиск→выбор→Backend→PostgreSQL→React; KJ видит заказ.
    * Тест 2 — подтверждение: KJ подтверждает → песня в очереди VDJ.
    * Тест 3 — двойное нажатие: два клика "Подтвердить" → в VDJ только одна песня.
    * Тест 4 — ошибка VDJ: VDJ недоступен → status=error, песня не считается добавленной.
    * Тест 5 — несколько заказов: разные столы с разным числом заказов, KJ видит все.
    * Тест 6 — несколько клубов: KJ клуба 1 видит только заказы клуба 1.
    * Тест 7 — отклонение: KJ отклоняет → rejected → уведомление гостю.
    * Тест 8 — перезапуск: после рестарта backend заказы не теряются (Postgres хранит), React подтягивает актуальное состояние, бот продолжает работать.
43. Критерий готовности — основной сценарий реализован, когда полностью работает вся цепочка: Гость → существующий бот → поиск → выбор → Backend API → PostgreSQL → React KJ Panel → KJ "Подтвердить" → Backend → VirtualDJ → песня в очереди → status=queued → уведомление гостю; при этом весь старый функционал karaoke_pro продолжает работать.
44. Ключевое требование — это доработка существующего проекта, не переписывание с нуля.
    Нужно: использовать существующий код и логику, сохранить существующие функции, добавить Backend API, React KJ Panel, PostgreSQL для нового процесса заказов, интеграцию с VirtualDJ, защиту от двойного заказа, WebSocket, при необходимости расширить поиск через Claude+Genius.
    Нельзя: создавать новый независимый бот, удалять существующий функционал без нужды, удалять старую БД без миграции, придумывать несуществующий API VirtualDJ, менять старую бизнес-логику без проверки её зависимостей.
