## 0. Самое важное — если читать только один раздел

1. **Только 2 из 5 живых способов создать заказ доходят до новой Backend-системы.** Мой `backend_client.post_order_to_backend()` встроен только в `handle_service_selection` (`bot.py:1281`, обычный инлайн-поиск гостя) и в AI-поиск (`ai_search_handlers.py`). Ручное добавление KJ (`bot.py:1144`), заказ через меню VIP (`vip.py:434`), избранное VIP (`vip.py:597`) и избранное обычного клиента (`client.py:407`) — **никогда не появятся** в Postgres/KJ Panel/VirtualDJ, даже теоретически, потому что вызов туда просто не добавлен в эти хендлеры. Это не баг, а объём работы, который ещё не сделан — но именно он определяет, насколько единой будет "единая очередь" из задачи №2.

2. **Найден денежный баг в живом (реально работающем) коде.** `replace_svc_execute` (`bot.py:892-907`, кнопка "🔄 заменить песню") проверяет баланс VIP перед заменой услуги, но **не списывает и не возвращает деньги** — просто переписывает `service_id` в заказе напрямую SQL. Итог: VIP может подменить бесплатную услугу на платную и получить её бесплатно; либо подменить дешёвую на дорогую — спишется по старой цене, но кэшбэк и статистика посчитаются по новой (при завершении заказа берётся актуальный `service_id`).

3. **Кнопка "KJ добавляет заказ вручную на стол" (`add_execute_`, `handlers/kj.py:2728-2755`) — не просто содержит баг вызова `create_order`, а весь этот путь недостижим в обычной навигации бота.** FSM-состояние `AddOrderForm.song_search`, которое должно его запускать, нигде не устанавливается (`state.set_state(...)` для него нет ни разу во всём репозитории). Рабочая версия той же функции — другая цепочка, через инлайн-поиск (`bot.py:695-744`), она корректна. Практический смысл: старая кнопка при обычном использовании даже не откроется, а не "откроется и упадёт".

4. **Аналогичный мёртвый дубль есть и для "заменить песню"** (`order_replace_execute`/`replace_song_`, `kj.py:2797-2821`) — тоже никогда не вызывается, реальная реализация — `bot.py:861-907` (та самая, где денежный баг из п.2).

5. **Подавляющее большинство операций с деньгами и заказами в `kj.py`/`admin.py` не проверяют роль вызывающего внутри самой функции** — только тем, что кнопка не показана другим ролям в клавиатуре. Из ~150 обработчиков `kj.py` явную проверку роли имеют только 9. Это не абстрактный риск: сюда входит подтверждение/отклонение/удаление заказа, изменение баланса VIP, удаление пользователя со всеми его данными, блокировка клиента, массовый сброс ролей клуба.

6. **Блокировка KJ через админ-панель визуально работает, но не имеет эффекта.** `BlockedUserMiddleware` (`bot.py:78-100`) проверяет `is_blocked` только для ролей `>= ROLE_VIP` (то есть VIP/USER/NO_TABLE) — ADMIN и KJ исключены из проверки полностью, хотя кнопка "заблокировать KJ" в админке существует и меняет тот же флаг в БД.

7. **Три экземпляра одного и того же метода `search_songs` в `database.py`** (строки 1242, 1473, 1688) с разной логикой — работает только последний по порядку в файле (Python-семантика переопределения метода), первые два — недостижимый код. Реальной ошибки это не даёт (вызовы совместимы с активной версией), но это явный след незамеченного слияния/рефакторинга и стоит убрать перед тем, как переносить логику поиска песен в новую систему.

8. **Функция "выполнен заказ" в старой системе — это не просто смена статуса, а начисление VIP-кэшбэка + обновление дневной статистики + пересчёт очереди** (`kj.py:1616-1660`). Confirm через новую KJ Panel ничего из этого не делает — см. подробный разбор в предыдущем сообщении в этом чате. Здесь подтверждаю: это не единственное такое место — `order_reject`, `order_delete_confirmed`, `table_close_execute` тоже делают возврат денег (`refund_vip_for_order`) при отмене, и тоже никак не связаны с новой системой.

9. **Статистика `daily_stats`, которую считает `update_daily_stats`, фактически ничем не читается.** Ни один экран админских "Отчётов" не обращается к таблице `daily_stats` — все отчёты (`report_today/week/month/venues/cashback`, CSV-экспорт) считают выручку заново прямыми JOIN-запросами к `orders`+`services`. `daily_stats` — write-only с точки зрения текущего UI. Если новое расширение планировало опираться на эту таблицу как на готовую агрегацию — она никем не проверена в проде.

10. **Реальный разнобой часовых поясов**: `created_at` во всех таблицах — `CURRENT_TIMESTAMP` SQL (UTC), а `completed_at`/`started_at`/`cancelled_at` заказа — `datetime.now()` в Python (локальное время сервера, без timezone). Это напрямую искажает `update_daily_stats`, `avg_wait_time`, и даёт разные числа "выручка за неделю" в разных экранах админки (один считает границу периода в Python локальным временем, другой — в SQLite через `DATE('now', ...)`, то есть в UTC).

## 1. Роли: константы, хранение, полная карта проверок

### 1.1 Константы (`config.py:10-15`)
```
ROLE_NONE = 0
ROLE_ADMIN = 1
ROLE_KJ = 2
ROLE_VIP = 3
ROLE_USER = 4
ROLE_NO_TABLE = 5
```
Роль — обычное целое поле `users.role` (`database.py:37-46`), без CHECK-ограничения, без справочной таблицы. Иерархия проверок (`role <= X` пропускает более привилегированные роли) — чистая договорённость кода, нигде не задокументированная и не вынесенная в одну функцию: `admin.py:39` использует строгое `!=` (только ADMIN), `kj.py:80` — `role > ROLE_KJ` (пропускает ADMIN и KJ), `vip.py:32` — `role > ROLE_VIP` (пропускает ADMIN, KJ, VIP).

VIP — не только роль, а ещё и отдельная запись в таблице `vip_clients` (per-venue: `balance`, `cashback_percent`, PK `(user_id, venue_id)`). Это два независимых состояния: `role=VIP` без записи в `vip_clients` даёт "VIP-меню с балансом 0"; запись в `vip_clients` без `role=VIP` вообще не всплывает в UI, пока роль не восстановится при `/start`.

### 1.2 Как назначается каждая роль

| Роль | Механизм | Код |

Важно: "Стать VIP" (`client_become_vip`, `client.py:819-836`) сама по себе ничего не меняет в БД — это только экран с описанием, реальная эскалация идёт через отдельную заявку. Самостоятельного пути "клиент сам себе выдаёт VIP" в коде нет.

### 1.3 "Клиент без стола" — двойное определение одного состояния
Есть роль `ROLE_NO_TABLE` **и** независимый структурный признак `table_number > venue.table_count` (используется как "виртуальный стол" в `utils.is_virtual_table`, `client.py:675-678`, `bot.py:1273` и др.). Они объединяются через `or` в некоторых местах (`bot.py:1273: is_no_table = user.role == ROLE_NO_TABLE or is_virtual_table(...)`), но не везде. Если KJ уменьшит `table_count` клуба после того, как у части клиентов уже назначены номера столов выше нового значения, эти клиенты структурно станут "виртуальными" без изменения `role` — рассинхронизация.

### 1.4 Карта меню по ролям (кто что видит)

- **Client** (`client_kb.py`): заказ песни, мои заказы/очередь, стать VIP, чат с KJ, (если админ своего стола) управление столом.
- **VIP** (`vip_kb.py`): то же самое + баланс (пополнение/история/финансы), без кнопки "стать VIP".
- **KJ** (`kj_kb.py`): "Настройки клуба" (импорт CSV, услуги, столы, VIP-настройки, чат-переключатель, бесплатные опции, клиенты — поиск/привязка/баланс/блокировка/удаление) и "Работа вечера" (очередь по столам, глобальная очередь, статистика).
- **Admin** (`admin_kb.py`): клубы (создание/правка/блокировка/удаление/назначение KJ/финансы/QR), KJ (назначить/снять/статистика/блокировка), отчёты (сегодня/неделя/месяц/по клубам/кэшбэк-комиссия/CSV), система (мониторинг/логи транзакций/**бэкап БД файлом в чат**/рестарт-заглушка).

Отдельно от `config.ROLE_*` существует локальная привилегия **"админ стола"** (`table_groups.admin_user_id`) — первый, кто занял стол, может управлять составом группы (кик/передача прав), это доступно и клиенту, и VIP одинаково, никак не связано с ролевой системой.

### 1.5 Проверено, но не найдено (важно знать, что искали и не нашли)
Помимо уже названных находок, специально проверялись и **не подтвердились** как отдельные баги: скрытая эскалация роли через прямой ввод текста в FSM-полях; SQL-инъекции в `update_venue_settings`/`update_service` (защищены тем, что ключи kwargs всегда из доверенного кода, но валидации имени колонки на уровне метода нет — это архитектурный риск, не рабочая уязвимость сейчас).

## 2. Схема данных — 13 таблиц SQLite

Полный список (`database.py:34-249`), без единого явного `CREATE INDEX` во всём файле (только PK/UNIQUE):

`users`, `venues`, `services`, `orders`, `vip_clients`, `songs`, `transactions`, `favorites`, `chat_messages`, `requests`, `table_groups`, `table_join_requests`, `event_log`, `daily_stats`.

Ключевые для задачи №2 — `orders` и `transactions`:

**`orders`**: `order_id, venue_id, table_number, user_id, service_id, song_name, status, created_at, completed_at, position, is_next, marked_next_at, started_at` + миграциями добавлены `artist_name, song_id, cancelled_at`. Эти три добавленных поля **не входят** в dataclass `Order` (`models.py`) — везде, где строка превращается в объект, код вручную делает `data.pop("artist_name", None); data.pop("song_id", None)` (`database.py:765-766, 784-785, 1645-1646, 1663-1664`). Забыть один `.pop()` в новом коде — гарантированный `TypeError`.

**`transactions`**: журнал движений денег, поле `type` принимает `'order_payment' | 'order_refund' | 'cashback' | 'topup'` — по коду, не по CHECK-ограничению в схеме.

**Статусы заказа** (все встречающиеся строковые литералы): `waiting → pending → completed`, ветки `cancelled`/`deleted` (обе используют одну и ту же метку времени `cancelled_at` — различить их можно только по значению `status`, не по времени). Статус `playing` **определён в схеме и используется в 6 SELECT-запросах** ("что сейчас играет" в клиентском/VIP/KJ интерфейсах), но **ни разу не устанавливается** ни одним вызовом `update_order_status` во всём репозитории — это чужой, оригинальный незавершённый функционал, из-за которого `started_at` никогда не заполняется, а следовательно `avg_wait_time` в статистике структурно нерабочий.

Сортировка очереди — единое правило в 5 местах: `ORDER BY is_next DESC, marked_next_at ASC, position ASC`. `is_next` переключается только вручную KJ/Admin (`toggle_order_next`, `kj.py:1031-1068`) — **VIP не получает приоритет в очереди автоматически**, несмотря на интуитивное ожидание.

## 3. Жизненный цикл заказа — все точки входа

Единственная точка `INSERT INTO orders` — `Database.create_order` (`database.py:732-750`), сигнатура: `(venue_id, table_number, user_id, service_id, song_name, status="pending")`.

| # | Путь | Кто | Начальный статус | Доходит до нового Backend? |
|---|---|---|---|---|
| 1 | Обычный инлайн-поиск гостя (`handle_service_selection`, `bot.py:1208-1289`) | любой (в т.ч. VIP) | `waiting` | ✅ да (`bot.py:1281`) |
| 2 | AI-поиск (`ai_search_handlers.py:172-179`) | любой | `waiting` | ✅ да |
| 3 | KJ добавляет вручную через инлайн (`kj_add_service`, `bot.py:1144-1190`) | KJ/Admin | `pending` | ❌ нет |
| 4 | Меню VIP "Заказать песню" (`vip.py:413-486`) | VIP | `pending` (без одобрения KJ!) | ❌ нет |
| 5 | Избранное VIP (`vip.py:597-604`) | VIP | `waiting` | ❌ нет |
| 6 | Избранное обычного клиента (`client.py:407-414`) | клиент/no-table | `waiting` | ❌ нет |
| 7 | "Добавить на стол" через мёртвую FSM-ветку (`kj.py:2741-2750`) | KJ/Admin (по замыслу) | падает раньше, недостижим | — |

Путь 4 — отдельная несостыковка внутри самой старой системы: один и тот же концептуальный "заказ услуги" в одном интерфейсе (обычный поиск) требует одобрения KJ (`waiting`), а в другом (меню VIP) — сразу встаёт в очередь (`pending`), без человека, проверяющего заказ. Оба одинаково списывают деньги в момент создания.

### Переходы статуса и их побочные эффекты

```
create_order(status=waiting|pending)
   │
   ├─ waiting → pending   : order_approve (kj.py:1538), без проверки роли
   ├─ waiting → cancelled : order_reject (kj.py:1575), без проверки роли → refund_vip_for_order
   ├─ pending → completed : order_complete_confirmed (kj.py:1616), без проверки роли
   │                        → apply_cashback (если платно и cashback%>0)
   │                        → update_daily_stats
   │                        → reorder_queue
   ├─ pending → deleted   : order_delete_confirmed (kj.py:1688), без проверки роли → refund_vip_for_order (до удаления)
   └─ pending/waiting → cancelled (пакетно, весь стол): table_close_execute (kj.py:1131), без проверки роли
                            → refund_vip_for_order в цикле по каждому заказу → update_daily_stats → unbind_table
```
Прямой SQL `UPDATE orders SET status='cancelled'` в обход `update_order_status` — один случай, `kj.py:1152-1157` (закрытие стола), функционально эквивалентен.

Есть вторая, недостижимая реализация закрытия стола (`table_close_confirm`, `kj.py:1806-1826`) — если бы была достижима, не вызывала бы `update_daily_stats`/`unbind_table`, то есть закрывала бы стол не полностью. Оставлена как мёртвый код.

## 4. Деньги — полная механика

**Баланс** — `vip_clients.balance`, per (user_id, venue_id). `update_vip_balance(add=True/False)` — относительное изменение, **без проверки на уход в минус** (нет constraint в схеме, нет проверки в коде метода — защита только там, где вызывающий код сам сверяет баланс перед списанием).

**Списание при заказе** (`charge_vip_for_order`, `database.py:932-938`) — происходит **в момент создания заказа**, а не при подтверждении/выполнении. Записывается транзакция `'order_payment'` с положительной суммой (знак трактуется по `type`, не по значению).

**Кэшбэк** (`apply_cashback`, `database.py:1412-1426`) — `round(price * cashback_percent/100, 2)`, начисляется **только** при `pending → completed`, только если услуга платная и у клиента `cashback_percent > 0`. Ставка кэшбека — per-client, хранится в `vip_clients.cashback_percent`; отдельно существует `venues.vip_cashback` — это **витринное** значение для UI (описание клуба), фактически в расчёте кэшбека не участвует.

**Возврат** (`refund_vip_for_order`, `database.py:940-980`) — идемпотентен (проверяет, не было ли уже `'order_refund'` по этому `order_id`), сумма берётся из исходной `'order_payment'`-транзакции (не из текущей цены услуги — это специально защищает от изменения цены задним числом), но именно поэтому усугубляет денежный баг замены услуги (см. п.0.2): при замене услуги без пересчёта платежа возврат всё ещё честный (вернёт то, что реально списали), а вот кэшбэк при завершении посчитается по новой (изменённой без оплаты) цене — асимметрия в пользу гостя.

**Топ-ап** — двухшаговый: заявка (`create_request(type='topup')`, `vip.py:182-203`) → одобрение KJ (`topup_request_approve`, `kj.py:1403-1475`, **с** проверкой роли) → `update_vip_balance(add=True)` + `record_transaction('topup')`. Деньги не зачисляются автоматически, без явного нажатия KJ.

**Важный крайний случай**: `update_vip_balance` — чистый `UPDATE ... WHERE user_id=? AND venue_id=?`, без `INSERT OR IGNORE`. Если у пользователя ещё нет строки в `vip_clients` (VIP-статус никогда явно не выдавался), любое зачисление молча обновит 0 строк — деньги "теряются" без ошибки.

## 5. Админка и отчётность

Admin **не управляет** ни услугами клуба (это исключительно KJ, `kj.py:190-381`), ни VIP-настройками — видит только производные метрики. Кнопка "💰 Кэшбек" в отчётах Admin — это **комиссия платформы** (`config.ADMIN_COMMISSION=0.05` от общей выручки), не имеет отношения к VIP-кэшбеку гостей, несмотря на название.

Найденные баги, специфичные для админки:
- `report_today` (`admin.py:920-926`) делит выручку клуба на **растущую частичную сумму**, а не на итог по всем клубам — проценты долей клубов в отчёте математически неверны (первый клуб в списке почти всегда покажет ~100%).
- `unbind_all_tables`/`unbind_all_venue_users` (`database.py:445-459, 477-483`) не имеют `return` — админ всегда видит "Отвязано: *None чел.*" вместо реального числа.
- `daily_stats` — как указано в п.0.9, полностью write-only, ни один отчёт её не читает; агрегаты `unique_users`, `new_users`, `total_topups`, `total_cashback`, `total_songs_played` (на деле дублирует `completed_orders`), `avg_wait_time` (структурно сломан из-за отсутствия `playing`-статуса) — никем не используются в проде.
- Рассинхронизация часовых поясов между способами расчёта периода (Python `datetime.now()` в одном экране, SQLite `DATE('now', ...)` UTC в другом) — см. п.0.10.
- `system_backup` (`admin.py:1208-1229`) копирует файл `.db` без WAL-чекпоинта и без файлов `-wal`/`-shm` — бэкап может не содержать последних закоммиченных, но ещё не перенесённых из WAL транзакций.

## 6. VIP и клиент без стола — специфика

- **Лимит активных заказов** (`config.MAX_ACTIVE_SONGS_PER_USER=2`) одинаков для всех ролей, включая no-table. Более того, он проверяется непоследовательно: есть в пути "заказ из избранного" (`fav_reorder` у обеих ролей), но **отсутствует** в основном пути заказа новой песни (`select_service`/`vip.py:413-486`) — то есть первый способ заказать песню лимитом вообще не ограничен ни для кого.
- **Расхождение проверки баланса при заказе из избранного**: `vip.py` проверяет баланс до создания заказа и блокирует при недостатке средств; `client.py` (тот же сценарий для обычного клиента) создаёт заказ без проверки и лишь потом пытается списать деньги, если `vip` не `None` — для настоящих не-VIP клиентов платная услуга из избранного фактически создаётся бесплатно.
- **Клиент без стола физически не имеет собственной логики** — `no_table_client.py` (106 строк) только назначает виртуальный номер стола и сразу передаёт управление в `handlers/client.py`. Вся его функциональность (заказ, избранное, чат, лимиты) — код обычного клиента, применённый к виртуальному номеру. Он корректно подмешивается в общую очередь наравне со столами при `table_mode == "sequential"` (round-robin, `client.py:685-769`), но в `vip.py::vip_queue` виртуальные столы вообще не помечаются отдельно (нет даже текстовой метки "без стола" — в отличие от клиентской версии той же очереди).

## 7. Маршрутизация — порядок роутеров и "теневые" перехваты

Регистрация (`bot.py:1375-1381`, порядок важен — aiogram матчит первым подошедшим):
```
admin.router → kj.router → vip.router → client.router → no_table_client.router → ai_search_router → kj_panel_router
```

Мои два новых роутера подключены **последними**. Проверено отдельно (`grep` по всему репозиторию): команды `/ai`, `/kjpanel` и callback-префиксы `ai_pick_`, `ai_svc_` нигде больше не используются — коллизий с существующими роутерами нет, это безопасно.

Внутри же самой оригинальной системы порядок создаёт реальные проблемы (это чужой, не мой код):
- Незащищённый `admin.py:1256` (`F.data.startswith("cancel_")`) стоит первым в списке роутеров и перехватывает идентичный по префиксу callback у `kj.py:2823`, `vip.py:1079`, `client.py:1006` — сейчас не эксплуатируется только потому, что реальные кнопки с таким префиксом генерирует лишь сама admin-клавиатура, но `kj_kb.py` содержит идентичную (сейчас неиспользуемую) `get_confirm_keyboard` — если её когда-нибудь подключат в `kj.py`, KJ, нажавший "Отмена", попадёт в панель администратора с финансовой сводкой по всей сети клубов.
- `vip.router` подключён раньше `client.router` → любой callback `order_replace_*`/`order_action_*`/`vip_chat_reply_*`/`cancel_*` без явной делегации в этих хендлерах молча обслуживает **все** роли через VIP-код, а не только VIP. Соответствующие "клиентские" версии этих функций (`client.py:581` без декоратора, `client.py:987`) — недостижимый мёртвый код.

Нет ни одного глобального обработчика ошибок (`dp.errors`) — все хендлеры полагаются на собственные `try/except`.

## 8. Полный список находок для трекинга (по серьёзности)

**Деньги:**
1. `replace_svc_execute` (`bot.py:892-907`) не списывает/не возвращает деньги при замене услуги в заказе — прямой финансовый риск. *(живой код)*
2. `update_vip_balance` без `INSERT OR IGNORE` — зачисление молча теряется, если у пользователя нет строки в `vip_clients`. *(живой код, крайний случай)*

**Безопасность/права:**
3. Блокировка KJ через админку не имеет эффекта (`BlockedUserMiddleware` исключает роли ADMIN/KJ). *(живой код)*
4. Подавляющее большинство денежных/деструктивных операций в `kj.py`/`admin.py` не проверяют роль внутри хендлера — защита только через видимость кнопки. *(живой код, архитектурный риск)*
5. `reset_venue_roles` использует литералы `(1, 2)` вместо констант ролей — молча разойдётся с `config.py` при любом будущем изменении номеров ролей. *(живой код)*

**Мёртвый код (не влияет на прод, но может ввести в заблуждение при доработке):**
6. `add_song_/add_service_/add_execute_` (`kj.py:2622-2755`) — недостижимая ветка с багом вызова `create_order` + падением ещё раньше на `Song.artist_name`/`sqlite3.Row`.

8. Второй `table_close_confirm` (`kj.py:1806-1826`) — недостижимый неполный дубль закрытия стола.
9. Три версии `search_songs` в `database.py` — работает только последняя.
10. `client.py:581 order_replace` без декоратора, `client.py:987 client_chat_reply` — недостижимы из-за порядка роутеров, реально обслуживаются `vip.py`.
11. `admin.py:1263` — недекорированный огрызок `admin_venues`.

**Отчётность/статистика:**
12. `daily_stats`/`update_daily_stats` — write-only, ни один отчёт её не читает.
13. `report_today` — неверный расчёт процента доли клуба (растущий частичный итог вместо общего).

**Интеграция со новой системой (это не баги старого кода, а объём работы для задачи №2):**
